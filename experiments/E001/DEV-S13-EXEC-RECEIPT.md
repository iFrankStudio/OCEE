## 为什么程序哈希绑定还不够

S12 的报告只声明了 `source_id`、`subject_program_hash`、`input`、`observed_after_step`。前两者可以阻止把**另一份程序**的报告误用在当前工具，但对于**同一程序、同一输入先后执行两次**，旧报告依然通过 S12 校验。这是一个不同于简单哈希字符串不匹配的、可以实际制造的重放案例。

## S13 的可执行变化

1. 世界在一次 `Action::Exec` 产生 `Code::Ok` 或 `Code::InvalidCode` 时，向反馈 `ActionResult` 增加 `exec_step`，记录这次动作的世界逻辑步；对 `Gas` 拒绝或其他非执行反馈**不签发该字段**。新增字段为可选 `u32`，只针对当前开发世界 `step <= u32::MAX` 的运行范围；超范围时不发回执，**不能宣称超过该范围仍有可用防重放功能**。
2. 同一个活动 VM 不换主程序。它在已注册工具的初次空输入 `EXEC` 后，将实际执行反馈完整保存到 `/self/repair/probe/receipt`，再依照 S12 路线读取两条世界模拟见证。
3. 个体已经检查来源声明、程序哈希、任务和输入后，对两份报告分别执行 `JsonFieldU32(report, "observed_after_step") == JsonFieldU32(receipt, "exec_step")`；只有都匹配，才继续旧工具功能比较、有限两候选修复、回归验证和 CAS 更新。
4. 不匹配时写入 `/self/repair/provenance/status = replayed_execution`，以未解决状态结束，**不**覆盖现有工具。

## 证据、消融与真实负面结果

| 条件 | 结果 |
|---|---|
| seed 5、17、2，正常本次执行反馈 | 继续原有语义修复；新版本正确、CAS 采用 |
| seed 0 原工具已正确 | 不作多余修改 |
| seed 20、23，证据缺失或冲突 | 不采用 |
| **事先真实执行同一程序、同一空输入**，seed 5、17 | 世界发布的是**真实有效但属于较早动作的报告**；活动 VM 后来自己再次执行完全相同输入，因新回执步数不同，**拒绝重放** |
| 关闭 S13 执行步检查，仅保留 S12 来源/程序检查 | 旧报告仍可被接收并触发修复；证明新增机制对这一案例必要 |
| 双通道都被特权研究者伪造成相同错误值，并保留**本次真实执行步数**，seed 5 | **负面结果**：仍会采用错误补丁；回执绑定不能认证来源或证明数值正确 |

测试还验证每个完成个体的执行反馈中存在内核签发的 `exec_step`，其值与真实世界审计记录中该次 `EXEC` 步数一致，并检查世界快照重放一致性。

## 科学与安全边界

**研究者明确预置**：空输入 `[]`、双模拟报告语义与世界真值、S6 的有限工具合成、S8 的 `[1,0]` 两候选修复、S12 的来源/版本检查，以及 S13 的回执保存和比较程序。这是**同一活动个体执行事先设计好的防重放策略**，不是它独立发现了时间、信任、签名或异常修复算法。

**未解决**：模拟报告无真正独立的身份与密码学认证；签发回执与报告的仍是同一世界内核，特权攻击者可以共同污染。若世界开放同版本多次验证，需要定义覆盖/更新和过期规则；S13 仍使用只发布一次的世界对象，不能表示通用多请求协议。逻辑步序号限于 `u32` 开发范围，不是通用随机挑战或不可预测的 nonce。研究者发起的早期世界动作可以构造合法但过期的旧报告；已验证 S13 对**此种具体同版本重放**能拒绝，不能据此宣传现实联网环境中的认证安全。

下一步不宜继续无限增加同源证据字段。优先开展 **S14 跨 episode 工具与记忆继承**：在新的世界 seed、隐藏任务配置和资源账户下只带入个体合法保留的工具/记忆，检验是否能实实在在降低重新合成成本或提升能力；以后再评估 P1/P2 跨协议学习与独立校准。
