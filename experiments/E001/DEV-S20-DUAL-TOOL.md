# S20 — 活动 VM 双可执行协议工具的生成、继承、负迁移及累计成本（开发）

**日期**：2026-11-18。**工程/开发集结果，非 E001 正式校准或确认性结果。G0 GO，G1/G2 NO-GO。**

## 1. S19 留下的可证伪问题

S19 的活动 P1 VM 能将 REMOTE_EVAL 操作码与 HELLO 推得的校验键特化成可执行报文生成工具，并跨全新世界复用；但 RESULT 操作码依然由 S18 的 112 候选搜索重新发现，使继承同实例环境仅节省约 623 A gas 和一个世界 tick。

S20 试验：是否能**在同一个受计费活动 VM 内**，进一步将真实 C 响应中查到的 RESULT 操作码生成第二个可执行工具；下个新世界在合法 C 反馈核验后同时使用两个工具，减少重新试探；工具失效时能否单独回退而不丢弃其它有效能力？最终考察三世界累计 A gas，而非只报单次便宜的工具执行。

## 2. 运行实现及可审计先验

主程序：[s20_p1_transfer.rs](../../crates/organism-seeds/src/s20_p1_transfer.rs)；测试：[s20_p1_transfer.rs](../../crates/organism-seeds/tests/s20_p1_transfer.rs)。首批实现提交 [c08c384](https://github.com/iFrankStudio/OCEE/commit/c08c38440ec77fd4e0a383f75b55887d65b70609)，四对照提交 [67cb3d1](https://github.com/iFrankStudio/OCEE/commit/67cb3d16f7d12617c7a15a7013a24e1b283a6eb2)，三世界/快照复核 [89817fd](https://github.com/iFrankStudio/OCEE/commit/89817fdfd244ed71bcf141a0dbf3fecc98e1c3fd)。

程序在每个世界启动时只安装**同一份完整初始 VM 图**（由研究者撰写），后来不由宿主替换 active program；发现、生成、合法世界操作、工具采用/拒绝都在 VM 内执行并计费。

- 旧的 S19 `REMOTE_EVAL` 工具仍通过真实 C 的空负载 `BadBody` 反馈做兼容检查。
- 第一次 RESULT 搜索使用 S18 的 P1 有界 opcode 扫描，严格校验合法结果的帧方向、操作码、长度、成功状态、XOR 校验、request_id 17。之后活动 VM 使用 `RewriteOp` 改写**研究者已预置的 P1 通用可执行帧编码模板**的两个常量位，生成可计算当前 RESULT 请求的第二个程序。
- VM 自己计算带 `OCEE-PROGRAM-V1\0` 域分隔符的 SHA256 内容哈希，写入不可变 `/self/versions/<hash>`。只有隔离 `EXEC` 产生的字节**与 VM 内另一套独立构造的预期帧完全一致**，才写入 `/self/tools/p1-result-frame`；继承旧版本失效时使用 CAS(0) 替换注册引用。
- 新世界继承两个或一个注册工具时，研究端迁移驱动器只用通常受计费的 `WRITE` 导入**不可变工具程序及各自 registry hash**。不带走上个世界的工作结果、邮箱、续执行状态、生成器状态、资源余额或者特权 B 账本。
- 新世界先调用继承的 RESULT 程序进行隔离 `EXEC`，将结果通过真实 `SEND` 交 C，并根据返回合法 RESULT 帧验证**当前**公开 HELLO 推得的校验参数、操作码、消息方向、成功状态、长度和 request_id；若只见错误诊断、报文不合法或字段不符则丢弃本次结果尝试并回到原有有界扫描，不能把 `EXEC Ok` 或特权 B gas 当成结果成功。
- 工具只能组装 P1 请求，而 FOLD32 语义、三 u32 负载、所有报文格式及检测结构**全部已写在研究者的初始个体代码中**。不存在新原语、全新协议语法、一般性算法或工具自发发明；这一机制属于**先验模板实例化 + 实际经验继承**。

## 3. 真实 CI 结果

[首轮 CI #44339532162](https://github.com/iFrankStudio/OCEE/actions/runs/44339532162) 通过 **91 项**工作空间测试；包含新增 4 项核心实验：冷启动两个工具；双工具对单工具；双工具一起失效；只有 RESULT 失效但 REMOTE_EVAL 仍兼容。

[最终 CI #44340938612](https://github.com/iFrankStudio/OCEE/actions/runs/44340938612) 通过 **93 项**工作空间测试/0 失败，在原四项上追加了三世界累计继承和第二程序已写但未注册时的确定性快照恢复测试。所有成功工作返回都由研究端独立 FOLD32 算式验证，真实 B 每个世界调用一次、计费 20 gas。标准 A 资源授予配额 12,000 gas/epoch，无任何宿主免费求解器在活动路径内替个体探索。

### 3.1 同一目标世界的消融计量

所有目标世界的 `config.seed=128`、`protocol.seed=42`、家族 P1。用 donor `config.seed=42/protocol.seed=42` 的活动 VM 已构造工具做继承，且目标世界工作项完全重新产生。

| 目标 episode 策略 | A 生命周期总 gas | 世界 tick | 继承写入 gas | B gas |
|---|---:|---:|---:|---:|
| 无工具继承、从头发现两 opcode 并创建两工具 | 8,354 | 136 | 0 | 20 |
| 只继承 REMOTE_EVAL 可执行工具，RESULT 冷搜索 | 7,731 | 135 | 62 | 20 |
| **继承两个可执行工具并分别核验** | **3,851** | **33** | **124** | **20** |

同初始程序、同资源口径，双工具对冷启动节省 **4,503 A gas（53.90%）**、103 tick（75.74%）；对只继承 REMOTE_EVAL 的策略节省 **3,880 A gas（50.19%）**。双工具需要额外 62 gas 的导入成本也已计入，非免费复制。

### 3.2 错误经验的实际代价

- **两个工具均来自不兼容 P1 实例**（源 `protocol.seed=272`，目标42）：活动 VM 发出实际检测并拒绝，重新探索并 CAS(0) 替换两个工具，最终得到 B 的正确结果。目标 A gas **9,144 vs 全冷启动 8,354**，负迁移 **+790 gas**，tick **154 vs 136**；总导入 124 gas，B 20。
- **只有 RESULT 工具不兼容**（REMOTE_EVAL 来自兼容源42，RESULT 来自不兼容源272）：活动 VM `EXEC` 旧结果工具并观察 C 的真实拒绝反馈，保留兼容的 REMOTE_EVAL 工具，仅重新搜索/注册 RESULT。A gas **8,120 vs 双工具兼容 3,851**，多 **4,269 gas**，两个导入仍为124 gas。REMOTE_EVAL registry version 仍为0，RESULT registry version 从0 CAS 更新至1，B 仍20。**局部恢复，而非删除全部工具。**

以上对照只包含 P1 家族内部的实例变化，不是 P1→P2 跨语法成功。

### 3.3 三个新世界的累计成本（包括第一轮学习）

三个 episode 的 world seed 依次 42→128→129，**协议实例种子都为42**，所以工具规则兼容；每次公开 FOLD32 数值不同。各个世界的 A、B 与存储账户完全独立；研究端只复制两个程序版本和两个 registry hash，经世界普通 WRITE 扣费。所有世界完成 B 任务，每轮 B gas20、累计60。

| 三 episode 合计 | A 总 gas |
|---|---:|
| 第一轮及后两轮均冷启动 | 25,064 |
| 第一轮学习，后两轮继承两个工具 | **16,056** |
| **累积节省** | **9,008（35.94%）** |

第二、第三新世界的双工具 A gas 各 3,851，完整冷启动分别 8,354/8,356；两次导入各124，**学习成本首轮 8,354 并未被排除**。这证明的是在事先同一协议实例可复用时，现有工具可减少后续相同工作种类的探索成本；不证明未知结构跨协议的长期开放式演化。

### 3.4 快照/故障边界

[CI #44340938612](https://github.com/iFrankStudio/OCEE/actions/runs/44340938612) 还通过了一个非任意 tick 检查点：第一工具已注册，**第二个不可变 RESULT 版本已写入但 `/self/tools/p1-result-frame` 尚未注册**。从此状态恢复世界快照，与原轨迹分别继续执行，最终世界状态哈希相等、两个注册工具哈希相等，B 均只计费20。这是主机持久化重启的确定性回归，不是个体主动自救或自行迁移。

## 4. 初始个体/能力来源及未达研究目标

当前 S20 初始程序由研究者预写 P1 的定界转义、XOR、帧字段、112 opcode 边界、BadBody 诊断选择、RESULT 帧验证规则、双可执行模板和两个 literal 替换位，甚至兼容性/回退策略。因此，活动 VM 的**实例级工具生成和积累被验证**，但**产生全新的、原先未知结构的协议语法或发明新算法仍未验证**。
